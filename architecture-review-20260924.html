1 · Give the stage protocol one interface, and the run types one dispatch

Strong in-process

execution/aa_workflow.py:14-184 · execution/cg_adapter.py:21-291 · execution/composition_workflow.py:12-62 · execution/workflow.py:13-88 · execution/coordinator.py:416-438, 494-636 · execution/admission.py:8-39 · web/routes/runs.py:12-43

Before — four protocol modules, dispatch in six places
After — one protocol interface, one dispatch seam
Problem
Four modules answer one question — what stages exist, which settings are legal, is this runnable, how is it prepared — in three incompatible shapes, and the dispatch that chooses between them is smeared across routes, admission, the coordinator and the workflow.
Solution
One protocol interface in workflow.py that every run type satisfies as an adapter, with the run-type matrix enforced once at the seam instead of six times above it.
Wins
  • leverage: one interface, every run type
  • locality: a new run type touches one file
  • settings validated once, not twice
  • readiness result has one shape
  • admission stops duplicating create_job
  • delete three parallel name lists

Contradicts the "three independent protocol modules" framing in docs/PROJECT_GUIDE.md:82-96 — worth reopening, because the independence is what makes every workflow change a four-file edit.

Evidence: SETTING_SPECS is (lo,hi) in aa_workflow.py:48-50 and (label,lo,hi) in cg_adapter.py:63-72, so coordinator.py:560-565 hand-merges both dialects; three tool_metadata() bodies and three differently-keyed readiness dicts; the CG parse of AA settings rebuilds a legacy dict at coordinator.py:563.

4 · One root, resolved once: adapters stop using the import-time default

Strong in-process

execution/stage_io.py:12-24 · execution/coordinator.py:48-53 · execution/worker.py:28 · analysis/surfaces.py:65 · config/tools.json · cli/*

Before — two roots, three ways to find a tool
After — one environment module behind Paths
Problem
Adapters, readiness and tool probes resolve the project root, templates, force field and executables from a default captured at import, while the coordinator works against a selected workspace — and tool locations come from a PATH prefix typed into two modules rather than the config file that declares them.
Solution
One environment module that answers where is the workspace, the force field, the templates, this tool from the selected paths, with config/tools.json either honoured or removed.
Wins
  • one place knows the root
  • config stops describing fiction
  • tests point at a scratch tree
  • no copied GROMACS path
  • frozen tools resolve honestly
  • locality: PATH built once

Evidence checked in this checkout: grep -rn "tools.json" dashboard/ returns nothing outside the venv, stage_io.environment() hard-codes ~/Downloads/gromacs-2026.0/build/bin (a path that does not exist here), analysis/surfaces.py:65 repeats it, and the working GROMACS at /usr/local/gromacs/2026.3/bin/gmx is found only because it happens to be on the inherited PATH.

Top recommendation

Start with candidate 1 — the stage protocol

Every recent feature in the log (bonded generation, the molecule-combination panel, the sucrose validation workflow, in-place resume) touched the coordinator plus one of the three protocol modules, and each one paid the same tax: the same setting, the same readiness key and the same stage contract declared a fourth time. One interface there shrinks four of the other candidates — the coordinator's run-type branch (4), the duplicated protocol contract (7) and half of the web surface (6) — into ordinary edits.

If the next feature is the roadmap's mapping-refinement panel, start with candidate 3 instead: that panel lands exactly on the candidate-verdict cluster, so deepening it first means writing the feature once.
